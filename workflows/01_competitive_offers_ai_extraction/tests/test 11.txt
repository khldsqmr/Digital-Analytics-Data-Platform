## Verdict — can `hit_count > 1` replace the join?

**No, not for a precise non-bounce definition.**

- `hit_count > 1` **over-counts non-bounces by ~1.32M sessions per day (~26% inflation)** because it includes sessions where the user triggered multiple non-pageview events (link tracking, form impressions, errors, etc.) on a single page.
- Recall is excellent (99.9%) — virtually no true non-bounces are missed.
- Precision is only 79.5% — about 1 in 5 sessions flagged by `hit_count > 1` are actually single-pageview sessions with multiple interaction events.

**If your business definition of "non-bounce" is "viewed more than one page" (the standard Adobe/GA4 definition), `hit_count > 1` is NOT equivalent and you cannot drop the join.**

If your business definition is "did anything beyond opening" (any interaction at all), then `hit_count > 1` is a reasonable proxy — but even then, note that `hit_count = 1` is only 2.4% of sessions, so it's a weak discriminator.

## Is `hit_number_in_session` stable across source refreshes?

**Mostly yes, but with explicit correction semantics you need to handle.** From the SEF schema:

- `is_corrected` — flag indicating this row was corrected after initial write
- `superseded_by_hash` — points to the row that replaces this one
- `correction_reason` — why the row was corrected
- `event_version` — version number for the event, increments on correction
- `session_watermark_utc` — watermark indicating session processing time
- `updated_at_utc` — last update timestamp

**Pipeline freshness:** Last 7 days may shift as late events are repaired. Specifically, sessions can be **re-sequenced** if late-arriving events land after initial processing, which would cause `hit_number_in_session` to shift. The guarantees are:

1. **For sessions where `session_status = 'CLOSED'` AND older than ~7 days**: `hit_number_in_session` is stable.
2. **For sessions where `session_status = 'OPEN'` OR within the 7-day repair window**: sequencing may change as late events backfill. The first event of a session can be replaced by an earlier-timestamp event that arrives late.
3. **To get the latest/authoritative sequencing**: filter out corrected rows with `WHERE is_corrected = FALSE OR is_corrected IS NULL`, OR equivalently exclude `MERGED` / `SUPERSEDED` session statuses.

**Operational recommendation for Media Intelligence Platform:**

```
WHERE session_status IN ('OPEN', 'CLOSED')
  AND (is_corrected = FALSE OR is_corrected IS NULL)
  AND hit_number_in_session = 1
```

For stable historical analytics, lag your "first event" materialization by **7 days** behind the current date to let the repair window settle. For near-real-time use cases, accept that recent entry events can shift and refresh daily.

## Why `channel_name` drifts — root cause

`channel_name` is **recomputed per hit** by the Adobe Marketing Channel processing rules. On each hit, it looks at:
- Current page's `cmpid` / `extCampaign` query param
- `page_referrer`
- `page_url_full` landing context

If a user lands via Paid Search (`channel_name='Paid Search'`), then clicks an internal link carrying a different `cmpid` (e.g., an email promo link embedded in the page), the rules fire again and the next hit's `channel_name` reflects the new context. **This is Adobe's intended per-hit behavior, not a bug** — but it means `channel_name` is NOT a session-sticky attribution field by design.

Standard Adobe practice is to pair the per-hit `channel_name` with an eVar-based "First Touch Channel" or "Last Touch Channel" variable that persists for the whole visit. **Those persisted variables don't appear to be mapped into Silver today** — both `attribute_last_touch_channel` (0.08% fill) and `attribute_marketing_channel` (0.0% fill) are effectively absent.

- `deeplink_url` captures **the exact URL used to launch or navigate the app**. On entry (`hit_number_in_session=1`), it represents the **external deep link that opened the app** — a universal link, custom URL scheme (`tmobile://…`), or OS-handoff URL.
- On non-entry hits, `deeplink_url` can also populate when the user **follows an internal in-app deep link** (e.g., tapping a card in the home feed that resolves via the deep-link router). So **`deeplink_url` is NOT guaranteed to describe only the entry link** — on later hits it can describe mid-session navigation.
- Dictionary documents it as _"Deep link URL used to open the app or navigate within the app"_ — the "or navigate within" wording is the gotcha. **Filtering to `hit_number_in_session=1` is required** to isolate the entry attribution.

## Join strategy — which keys are cheapest

### `session_id` joins (SEF ↔ SSF)
**Cheapest join path in the entire schema.** `session_id` is clustered on SEF (as third key) and is the primary identifier on SSF (one row per session). Snowflake can use clustering to prune both sides. Use this join whenever your use case can be expressed at session grain — it's dramatically cheaper than hash joins on `row_identity_hash`.

### `row_identity_hash` joins (SEF ↔ UDI)
**The expensive join.** Neither UDI nor SEF has `row_identity_hash` as a clustering key, so Snowflake must do a hash join on billions of UDI rows after date-pruning both sides. **Required predicates to make this tolerable:**
1. `event_date_pst` on BOTH sides (identical value)
2. `source_table` on BOTH sides (identical value)
3. `row_identity_hash` as the equi-join condition

Without matching date and source_table predicates on BOTH sides, the join degenerates to a cross-partition hash and becomes catastrophically slow.

### Golden rule
- **If your question can be answered at session grain** (counts, flags, timing, identity) → join SSF to SEF on `session_id`, skip UDI.
- **If you need hit-level event attributes** (page name, flow, channel, LOB, geography) → SEF→UDI on `row_identity_hash` + date + source_table is the only path, and it should be pre-materialized nightly rather than run per-query.

- **Partition pruning: no.** Not a cluster key.
- **Row reduction after prune: ~99.4%.** Reduces SEF scan from 300M → 1M+ rows per day post-prune on web+app.
- **Join cost reduction: substantial.** The downstream SEF→UDI join on `row_identity_hash` goes from ~300M probe rows to ~6M — this is where the real win comes from.
- **Verdict: use it aggressively for entry-attribution use cases.** The filter is cheap and the downstream join savings are large.

| Use case | Recommended freshness lag | Rationale |

## No completion/readiness flag today — operational workarounds

Since neither table carries an explicit "data for date X is complete" flag, use these proxies:

1. **UDI readiness proxy**: query `MAX(event_collection_timestamp_pst)` for a date — if it's within the last 15 minutes, data is still arriving. If it's older than 24 hours, that date is settled.

2. **SEF/SSF readiness proxy**: query `COUNT(*) WHERE session_status = 'OPEN'` for a date — if the OPEN count is dropping day-over-day, closing is still in progress. Once stable (3–7 days post-date), the data is frozen.

3. **For automated pipelines**: compare row counts of a target date on day-N vs day-(N-1) runs. If counts changed by >1%, the data is still settling — wait another day before promoting to stable layer.

# Session-Level Geography — Production Pattern (UDI + SEF + SSF)

The three-table join at full daily scale times out from my sandbox role, but here's the **ready-to-run pattern** you can execute in your own warehouse. It gives one geo row per session.

## 🎯 Pattern 1: Session-level geography (any flow)

```
WITH event_geo AS (
  -- One geo row per session, picking the first non-null signal per hit
  SELECT
    e.session_id,
    MAX(CASE WHEN u.geo_postal_code     IS NOT NULL
             THEN LEFT(u.geo_postal_code, 5) END)       AS session_zip,
    MAX(u.attribute_country)                            AS session_country,
    MAX(u.coverage_map_location)                        AS session_coverage_loc
  FROM BDM_DBI_DB.SILVER_DIGITAL_INTERACTIONS.SESSION_EVENT_FACT e
  JOIN BDM_DBI_DB.SILVER_DIGITAL_INTERACTIONS.UNIFIED_DIGITAL_INTERACTIONS u
    ON  e.row_identity_hash   = u.row_identity_hash
    -- partition pruning on both sides is critical for performance
    AND u.event_timestamp_pst >= '2026-10-01'::DATE
    AND u.event_timestamp_pst <  '2026-10-02'::DATE
  WHERE e.event_timestamp_pst >= '2026-10-01'::DATE
    AND e.event_timestamp_pst <  '2026-10-02'::DATE
  GROUP BY e.session_id
)
SELECT
  s.session_id,
  s.session_start_date,
  s.source_table,                       -- 't_web_interactions' | 't_app_interactions'
  s.canonical_user_id,
  s.identity_status,
  s.session_had_purchase,
  eg.session_zip,                       -- web ~46% / app 0%
  eg.session_country,                   -- app ~100% / web 0%
  eg.session_coverage_loc,              -- both, <0.1% (coverage-map clicks only)
  z.STATE,                              -- joined from ZIP dim
  z.REGION,
  z.MARKET
FROM BDM_DBI_DB.SILVER_DIGITAL_INTERACTIONS.SESSION_SUMMARY_FACT s
LEFT JOIN event_geo eg USING (session_id)
LEFT JOIN BDM_MKTGANALYTICS_DB.FEDERATED_T.MKTGANALYTICS_V_GEO_DIM_ZIP z
       ON eg.session_zip = z.ZIP_CODE
WHERE s.session_status      IN ('OPEN','CLOSED')
  AND s.session_start_date   = '2026-10-01'::DATE
```

Define peer set and topline metrics.

### Impact on topline

**Plain version:** how much of the topline's movement this one value is responsible for. It answers "so what" rather than "how much did this change."

**Formula, counts:**

```
impact % = (slice current − slice baseline) ÷ topline baseline
```

The denominator is the topline, not the slice's own base. That's the whole trick.

**Example:**

```
Paid Search  (493,775 − 446,463) ÷ 1,720,000  =  +2.75%
SMS          ( 31,094 − 202,108) ÷ 1,720,000  =  −9.94%
```

Compare against what each did on its own base: Paid Search rose 10.6%, SMS fell 84.6%. Sorted by own change, SMS looks like the story of the week and Paid Search looks minor. Sorted by impact, SMS moved the topline by ten points and Paid Search by three. That ordering is the one you want in the weekly read.

## Versus peer set — worked through step by step

**The question it answers:** did this channel move differently from all the other channels?

### The setup

Channel breakout, Total UPV, week 7 compared to week 6.

Week 6

Week 7

**All channels together (topline)**

1,720,000

1,545,000

**Paid Search**

446,463

493,775

The topline fell. Paid Search rose. That gap is what we're measuring.

### Step 1 — What did Paid Search do?

```
493,775 − 446,463 = +47,312
+47,312 ÷ 446,463 = +10.6%
```

**Paid Search went up 10.6%.**

### Step 2 — What did every other channel do?

Take Paid Search out of the topline. What's left is the peer set: organic, direct, email, SMS, display, and the rest, all added together.

```
Week 6 peers:  1,720,000 − 446,463 = 1,273,537
Week 7 peers:  1,545,000 − 493,775 = 1,051,225
```

Now the same change calculation on that combined group:

```
1,051,225 − 1,273,537 = −222,312
−222,312 ÷ 1,273,537 = −17.5%
```

**Every other channel, combined, went down 17.5%.**

### Step 3 — The points gap

```
Paid Search:   +10.6%
Peer set:      −17.5%
Gap:            10.6 − (−17.5) = +28.1 points
```

**Paid Search finished 28.1 points ahead of the rest of the channel mix.**

### Step 4 — Turn that into volume

Points are hard to act on. So: what would Paid Search have looked like if it had behaved like everything else?

```
Apply the peer rate to Paid Search's starting point:
446,463 × (1 − 0.175) = 368,527
```

That's the counterfactual. Now compare it to reality:

```
Actual:            493,775
Would have been:   368,527
Excess:           +125,248
```

**125,248 UPV exists only because Paid Search moved against the tide.**

### How to say it out loud

> Every other channel dropped about 17% this week. Paid Search went up 10%. If it had dropped with everything else it would have come in around 369,000. It came in at 494,000. So roughly 125,000 visits are down to something happening specifically in Paid Search.

### The same four steps on SMS, for contrast

```
1. SMS:        31,094 vs 202,108     →  −84.6%
2. Peer set:   1,513,906 vs 1,517,892 →   −0.3%
3. Gap:        −84.6 − (−0.3)         =  −84.4 points
4. Would have been: 202,108 × 0.997   =  201,577
   Excess:     31,094 − 201,577       =  −170,483
```

The rest of the channels were flat. SMS fell off a cliff. Nothing systemic is going on, so the answer is entirely inside SMS.

### Two things the engineers need to know

**The peer set always uses the four-week trend**, whatever comparison the user has picked on screen. The example above uses prior week because it's easier to follow.

**Step 2 cannot be done by subtraction on real data.** It worked here because the sample file was built so the channels add up. Real UPV doesn't: one person visits through search and direct in the same week and counts in both, so the channels sum to more than the topline. Subtracting Paid Search from 1,720,000 would give the wrong peer figure.

On EDL, step 2 means going back to the visit-level table and counting distinct visitors across all channels except Paid Search. Then repeating that for every channel, every breakout, every metric, every week. Page views is the only metric where the shortcut is valid.

🧭 Entry-hit attribution pattern (recommended for sessions)
For proper session-level campaign attribution, you want the UTM from the entry hit only, then propagate across the session. That uses two more tables:

Supporting tables for session-level attribution
Table	Role
prd_dbi_analytics.silver_digital_interactions.session_summary_fact	Session grain — one row per session, has session_id, canonical_user_id
prd_dbi_analytics.silver_digital_interactions.session_event_fact	Event grain — has session_id, hit_number_in_session, row_identity_hash to join back to UDI
Join pattern
WITH entry_hit AS (
  SELECT
    e.session_id,
    u.page_url_full,
    u.external_campaign_code,
    REGEXP_EXTRACT(u.page_url_full, '[?&]utm_source=([^&#]+)',   1) AS utm_source,
    REGEXP_EXTRACT(u.page_url_full, '[?&]utm_medium=([^&#]+)',   1) AS utm_medium,
    REGEXP_EXTRACT(u.page_url_full, '[?&]utm_campaign=([^&#]+)', 1) AS utm_campaign
  FROM prd_dbi_analytics.silver_digital_interactions.session_event_fact e
  JOIN prd_dbi_analytics.silver_digital_interactions.unified_digital_interactions u
    ON  e.row_identity_hash = u.row_identity_hash
    AND e.event_date        = u.event_date
    AND e.source_table      = u.source_table
  WHERE e.event_date = DATE '2026-09-24'
    AND e.hit_number_in_session = 1       -- entry hit only
    AND e.source_table = 't_web_interactions'
)
SELECT
  s.session_id,
  s.canonical_user_id,
  s.session_start_date,
  s.session_had_purchase,
  eh.utm_source, eh.utm_medium, eh.utm_campaign,
  eh.external_campaign_code
FROM prd_dbi_analytics.silver_digital_interactions.session_summary_fact s
LEFT JOIN entry_hit eh USING (session_id)
WHERE s.session_status IN ('OPEN','CLOSED')
  AND s.session_start_date = DATE '2026-09-24'
  AND s.source_table = 't_web_interactions'

🧭 How to derive acquisition channel yourself
You can build "Paid Search / Organic / Direct / Email / Social" from signals you already have:

Signals available
Signal	Column	Source Table	Fill
UTM parameters (source/medium)	page_url_full / entry_page_url_full	UDI / SSF	Web only, ~10% of sessions
Adobe campaign code	external_campaign_code	UDI	Web ~6%, App 0.02%
Referring domain	entry_page_referrer	SSF (access-controlled)	Web only
Derivation pattern (session-level, web only)
SELECT
  session_id,
  entry_page_url_full,
  entry_page_referrer,
  REGEXP_EXTRACT(entry_page_url_full, '[?&]utm_medium=([^&#]+)', 1) AS utm_medium,
  REGEXP_EXTRACT(entry_page_url_full, '[?&]utm_source=([^&#]+)', 1) AS utm_source,
  CASE
    -- Paid search
    WHEN LOWER(REGEXP_EXTRACT(entry_page_url_full, '[?&]utm_medium=([^&#]+)', 1))
           IN ('cpc','ppc','paid','paidsearch','sem')
      THEN 'Paid Search'
    -- Paid social
    WHEN LOWER(REGEXP_EXTRACT(entry_page_url_full, '[?&]utm_medium=([^&#]+)', 1))
           IN ('paidsocial','social-paid','social_cpc')
      THEN 'Paid Social'
    -- Email
    WHEN LOWER(REGEXP_EXTRACT(entry_page_url_full, '[?&]utm_source=([^&#]+)', 1)) = 'email'
      OR LOWER(REGEXP_EXTRACT(entry_page_url_full, '[?&]utm_medium=([^&#]+)', 1)) LIKE '%email%'
      THEN 'Email'
    -- Organic search
    WHEN entry_page_referrer ILIKE '%google.com%'
      OR entry_page_referrer ILIKE '%bing.com%'
      OR entry_page_referrer ILIKE '%yahoo.com%'
      OR entry_page_referrer ILIKE '%duckduckgo.com%'
      THEN 'Organic Search'
    -- Organic social
    WHEN entry_page_referrer ILIKE '%facebook.com%'
      OR entry_page_referrer ILIKE '%instagram.com%'
      OR entry_page_referrer ILIKE '%twitter.com%'
      OR entry_page_referrer ILIKE '%t.co%'
      OR entry_page_referrer ILIKE '%linkedin.com%'
      OR entry_page_referrer ILIKE '%youtube.com%'
      OR entry_page_referrer ILIKE '%tiktok.com%'
      THEN 'Organic Social'
    -- Referral
    WHEN entry_page_referrer IS NOT NULL AND entry_page_referrer <> ''
      THEN 'Referral'
    -- Direct
    ELSE 'Direct / Unknown'
  END AS acquisition_channel
FROM prd_dbi_analytics.silver_digital_interactions.session_summary_fact
WHERE source_table = 't_web_interactions'
  AND session_status IN ('OPEN','CLOSED')
  AND session_start_date = DATE '2026-09-24'

Metro App: site_name = 'Metro App' OR site_name LIKE '%Metro App%' → ~32M hits/day combined (3.9% standalone + 7.5% in combo = ~11% of all app hits touch Metro)
TRetail App: site_name = 'TRetail App' OR site_name LIKE '%TRetail App%' → ~18M hits/day combined (~6% of all hits involve the retail employee app)
Metro web: site_name = 'MbyT' → ~1M hits/day
🔧 Clean property breakdown
CASE
  WHEN site_name ILIKE '%Metro App%'    THEN 'Metro App'
  WHEN site_name ILIKE '%TRetail App%'  THEN 'Retail App'
  WHEN site_name ILIKE '%TLife App%'    THEN 'T-Life App'
  WHEN site_name ILIKE '%MbyT%'         THEN 'Metro Web'
  WHEN site_name ILIKE '%T-Mo Prepaid%' THEN 'Prepaid Web'
  WHEN site_name ILIKE '%TFB%'          THEN 'TFB Web'
  WHEN site_name = 'TMO'                THEN 'T-Mobile Web'
  WHEN site_name ILIKE '%Expert Assist%' THEN 'Expert Assist'
  WHEN site_name ILIKE '%TMO Concierge%' THEN 'Concierge'
  ELSE 'Other'
END AS property
🪤 Important for your Bronze projection
Your current MIP pipeline uses source_table + page_app_type to distinguish properties, but site_name is the finer-grained signal — especially for separating TLife vs Metro vs TRetail, which all share source_table = 't_app_interactions'.

If downstream consumers need to split Metro from TLife or exclude retail-employee traffic, add site_name to your projection (it's already in your SELECT list — good) and build the property CASE above in a Silver enrichment step.
